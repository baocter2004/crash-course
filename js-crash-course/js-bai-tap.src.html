2. Scope và chuỗi scope

Scope là vùng code mà một biến có thể được truy cập. JS có global scope, function scope và block scope. Khi đọc một biến, JS tìm ở scope hiện tại, không có thì tìm lên scope bao ngoài, cứ thế đến global. Đó gọi là scope chain. Scope được quyết định bởi vị trí viết code, không phải nơi gọi hàm (gọi là lexical scope).

const a = 'global';

function outer() {
  const b = 'outer';

  function inner() {
    const c = 'inner';
    console.log(a, b, c);   // inner thấy cả 3 biến
  }

  inner();
  console.log(typeof c);    // outer không thấy c của inner
}

outer();
Kết quả khi chạy
global outer inner
undefined

var chỉ biết đến function, nên nó lọt ra ngoài block if, for:

if (true) {
  var x = 1;
  let y = 2;
}
console.log(x);          // var lọt ra ngoài block
console.log(typeof y);   // let thì không
Kết quả khi chạy

undefined

Biến trong scope con có thể che (shadow) biến cùng tên ở scope ngoài. Biến ngoài không bị đổi.

3. Hoisting

Trước khi chạy, JS quét qua scope và đăng ký mọi khai báo. Vì vậy có cảm giác khai báo được "kéo lên đầu". Kết quả khác nhau tuỳ loại:

  • Function declaration: đăng ký cả thân hàm, gọi trước khi khai báo được.
  • var: đăng ký tên, giá trị là undefined cho đến dòng gán.
  • let, const, class: đăng ký tên, nhưng truy cập trước dòng khai báo sẽ ném ReferenceError. Khoảng từ đầu scope đến dòng khai báo gọi là Temporal Dead Zone (TDZ).
console.log(hello());      // gọi được: function declaration
console.log(v);            // undefined: var đã đăng ký, chưa gán

try {
  console.log(l);          // TDZ
} catch (e) {
  console.log(e.name);
}

function hello() { return 'xin chào'; }
var v = 1;
let l = 2;
Kết quả khi chạy
xin chào
undefined
ReferenceError

Function expression và arrow function là giá trị gán vào biến, nên chúng tuân theo luật của biến đó, không được hoist như function declaration.

4. Vòng lặp với var và let

Đây là câu phỏng vấn kinh điển. var tạo một biến duy nhất cho cả vòng lặp. let tạo một biến mới cho mỗi vòng. Callback của setTimeout chạy sau khi vòng lặp kết thúc (chương 7), nên nó đọc giá trị của biến lúc đó.

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log('var', i), 0);
}
for (let j = 0; j < 3; j++) {
  setTimeout(() => console.log('let', j), 0);
}

5. Biến toàn cục ngầm và strict mode

Gán vào một tên chưa khai báo: ở sloppy mode, JS âm thầm tạo biến toàn cục. Ở strict mode thì ném ReferenceError. File .mjs, code trong class, và code do TypeScript hay NestJS biên dịch đều chạy strict mode nên bạn thường được bảo vệ, nhưng vẫn cần biết để đọc code cũ.

Khác PHP: PHP tạo biến khi gán lần đầu và mỗi hàm có scope riêng biệt. JS bắt buộc khai báo, và hàm nhìn thấy biến bên ngoài. Viết count = 1 thiếu let trong JS không phải là cách khai báo biến.

Kiểu dữ liệu, so sánh, tham chiếu và bất biến

Đây là chương quan trọng nhất với React. Phần lớn lỗi "đã setState mà giao diện không đổi" đều do chưa hiểu tham chiếu.

1. Kiểu dữ liệu

JS có 7 kiểu primitive: string, number, bigint, boolean, undefined, null, symbol. Mọi thứ còn lại là object, kể cả array và function.

console.log(typeof [], typeof {});   // array cũng là object
console.log(typeof function () {});

2. So sánh và truthy/falsy

== ép kiểu trước khi so sánh, luật rất khó nhớ. === so sánh cả kiểu và giá trị. Luôn dùng ===. Ngoại lệ phổ biến duy nhất là x == null, đúng cho cả null và undefined.

Chỉ có 8 giá trị falsy: false, 0, -0, 0n, '', null, undefined, NaN. Mọi thứ khác đều truthy, kể cả [], {} và '0'.

Khác PHP: trong PHP, mảng rỗng [] và chuỗi '0' là falsy. Trong JS, cả hai đều truthy. Viết if (items) để kiểm tra mảng rỗng là sai, phải viết if (items.length > 0).

3. Ba toán tử giá trị mặc định

const qty = 0;
console.log(qty || 1);        // || lấy vế phải khi vế trái falsy: 0 bị thay
console.log(qty ?? 1);        // ?? chỉ thay khi null hoặc undefined: 0 được giữ

const user = { profile: null };
console.log(user.profile?.city);          // ?. gặp null/undefined thì trả undefined
console.log(user.profile?.city ?? 'N/A'); // kết hợp với ??

4. Giá trị và tham chiếu

Primitive được lưu và sao chép theo giá trị. Object được truy cập qua tham chiếu: biến giữ "địa chỉ", gán biến chỉ sao chép địa chỉ, không sao chép object. Hai object chỉ bằng nhau khi là cùng một object.

let a = 1;
let b = a;
b = 2;
console.log(a, b);           // primitive: độc lập

const arr1 = [1, 2];
const arr2 = arr1;
arr2.push(3);
console.log(arr1, arr2);     // cùng một mảng

console.log([] === []);      // hai mảng khác nhau
console.log(arr1 === arr2);  // cùng tham chiếu

5. Sao chép nông và sao chép sâu

Spread (...) chỉ sao chép một tầng. Object lồng bên trong vẫn dùng chung. structuredClone sao chép toàn bộ các tầng.

const original = { name: 'An', address: { city: 'Hà Nội' } };

const shallow = { ...original };
shallow.name = 'Bình';
shallow.address.city = 'Đà Nẵng';
console.log(original.name, original.address.city);

const deep = structuredClone(original);
deep.address.city = 'Huế';
console.log(original.address.city, deep.address.city);

6. Bất biến (immutability): lý do React cần nó

React so sánh state cũ và mới bằng Object.is, tức là so sánh tham chiếu. Nếu bạn sửa trực tiếp object rồi set lại, tham chiếu không đổi, React có thể không render lại. Vì vậy phải tạo object mới cho mỗi thay đổi.

const jobs = [
  { id: 1, title: 'PHP', company: { name: 'A' } },
  { id: 2, title: 'React', company: { name: 'B' } },
];

const byUser = orders.reduce((acc, o) => {
  acc[o.user] = (acc[o.user] ?? 0) + o.total;
  return acc;
}, {});

Closure

Closure là khái niệm khó nhất với người mới, nhưng cũng là nền tảng của toàn bộ React Hooks. Hiểu closure thì stale state, dependency của useEffect, và useCallback đều trở nên dễ hiểu.

1. Closure là gì

Closure là một hàm cùng với các biến bên ngoài mà nó nhớ được từ nơi nó được tạo ra. Biến đó vẫn sống sau khi hàm bao ngoài đã chạy xong, miễn là còn hàm bên trong dùng đến.

function createCounter() {
  let count = 0;             // biến này không bị xoá khi createCounter kết thúc
  return () => {
    count++;
    return count;
  };
}

const a = createCounter();
const b = createCounter();   // mỗi lần gọi tạo một count riêng

console.log(a(), a(), a());

4. Stale closure và React

1. Promise là gì

Promise là object đại diện cho kết quả sẽ có trong tương lai. Nó có 3 trạng thái: pending (đang chờ), fulfilled (thành công), rejected (thất bại). Đã chốt rồi thì không đổi nữa.

const sleep = (ms, value) =>
  new Promise((resolve) => setTimeout(() => resolve(value), ms));

5. Các bẫy hay gặp

  • forEach không chờ async: dùng for...of với await (tuần tự), hoặc Promise.all(list.map(...)) (song song).
  • Quên await: biến nhận được Promise chứ không phải dữ liệu. if (user) luôn đúng vì Promise là truthy.
  • return promise trong try: lỗi không bị catch của hàm đó bắt, phải viết return await promise.
  • fetch không reject khi gặp 404 hoặc 500: chỉ reject khi lỗi mạng. Phải tự kiểm tra res.ok.
  • Không truyền async vào useEffect trực tiếp: hàm async trả về Promise, trong khi React chờ một hàm cleanup. Khai báo hàm async bên trong rồi gọi.
  • Promise bị bỏ rơi (floating): gọi mà không await hay .catch. Từ Node 15, rejection không được xử lý sẽ làm sập process.

CHƯƠNG 7

Event loop

Câu hỏi "đoán thứ tự output" gần như chắc chắn gặp khi phỏng vấn JS. Quan trọng hơn, event loop giải thích vì sao một vòng lặp nặng có thể làm cả server NestJS đứng hình.

1. Mô hình

JS chạy trên một luồng, có một call stack. Tại một thời điểm chỉ có một đoạn code chạy, và đoạn đó chạy đến khi xong mới đến đoạn khác. Các việc chờ đợi (timer, mạng, đọc file) được giao cho môi trường bên ngoài (trình duyệt, hoặc thư viện libuv của Node). Khi xong, callback được đưa vào hàng đợi:

  • Microtask queue: callback của Promise (then, catch, finally), phần code sau await, queueMicrotask.
  • Macrotask queue (task queue): setTimeout, setInterval, I/O, sự kiện giao diện, setImmediate trong Node.

Thứ tự luôn là:

  1. Chạy hết code đồng bộ đang có trên stack.
  2. Chạy hết toàn bộ microtask, kể cả microtask mới sinh ra trong lúc này.
  3. Lấy một macrotask ra chạy, rồi quay lại bước 1.
console.log('1 đồng bộ');
setTimeout(() => console.log('4 macrotask'), 0);
Promise.resolve().then(() => console.log('3 microtask'));
console.log('2 đồng bộ');
Kết quả khi chạy
1 đồng bộ
2 đồng bộ
3 microtask
4 macrotask

setTimeout(fn, 0) không có nghĩa là chạy ngay. Nó nghĩa là "chạy sớm nhất có thể, sau khi stack rỗng và microtask đã hết". Delay là thời gian tối thiểu, không phải chính xác.

2. await chia hàm làm hai

Code trước await đầu tiên chạy đồng bộ ngay khi gọi hàm. Tại await, hàm dừng lại và trả quyền điều khiển cho nơi gọi. Phần sau await trở thành một microtask.

async function f() {
  console.log('A: trước await, vẫn đồng bộ');
  await null;
  console.log('C: sau await, là microtask');
}

f();
console.log('B: code sau lời gọi f');

3. Thêm chi tiết trong Node

Event loop của Node đi qua các pha, các pha chính gồm: timers (chạy setTimeout, setInterval) → poll (nhận kết quả I/O) → check (chạy setImmediate) → close. Sau mỗi callback, Node xử lý hết process.nextTick rồi đến Promise microtask.

API Chạy khi nào
process.nextTick Ngay sau thao tác hiện tại, trước Promise microtask (trong CommonJS)
Promise, queueMicrotask Sau code đồng bộ, trước macrotask
setTimeout(fn, 0) Pha timers
setImmediate Pha check, ngay sau poll

Ở file chính, thứ tự giữa setTimeout(fn, 0) và setImmediate không chắc chắn, tuỳ tốc độ máy lúc khởi động. Trong callback I/O thì setImmediate luôn chạy trước. Mình không đưa trường hợp không chắc chắn vào bài tập vì output có thể đổi giữa các lần chạy.

4. Vì sao Node "đơn luồng" mà vẫn phục vụ nhiều request

Khi một request await database, luồng JS không chờ mà đi xử lý request khác. Khi database trả lời, callback được đưa vào hàng đợi. Vì vậy Node rất hợp với công việc nhiều I/O.

Ngược lại, code tốn CPU (vòng lặp lớn, xử lý ảnh, JSON.parse file khổng lồ, bcrypt đồng bộ) không nhả luồng, nên mọi request khác phải chờ. Cách xử lý: chia nhỏ việc, dùng worker_threads, hoặc đưa ra process riêng bằng queue (NestJS Part 18).

Khác PHP: PHP-FPM có nhiều worker, một request chạy lâu chỉ giữ một worker. Trong Node, một đoạn code chặn sẽ chặn tất cả request trong process đó. async không tự làm code nhanh hơn hay chạy ở luồng khác: một hàm async tính toán nặng vẫn chặn event loop.

5. Trong trình duyệt

Trình duyệt vẽ lại giao diện giữa các macrotask, sau khi microtask đã hết. Code đồng bộ chạy lâu hoặc microtask nối tiếp nhau không dứt sẽ làm giao diện đơ. React dùng các cơ chế như useTransition để không chặn việc phản hồi người dùng khi render nặng.

  const hooks = [];
  let cursor = 0;
  let pending = [];

  function useEffect(fn, deps) {
    const i = cursor++;
    const prev = hooks[i];
    const changed =
      !prev || !deps || deps.some((d, k) => !Object.is(d, prev.deps[k]));
    if (changed) {
      pending.push(() => {
        prev?.cleanup?.();
        hooks[i] = { deps, cleanup: fn() };
      });

    cursor = 0;
    pending = [];
    const output = component(props);
    pending.forEach((run) => run());
    return output;
  }

}

  }
}

Code đáp án
class Emitter {
  #listeners = new Map();

  on(event, fn) {
    if (!this.#listeners.has(event)) this.#listeners.set(event, new Set());
    this.#listeners.get(event).add(fn);
    return () => this.off(event, fn);
  }

  once(event, fn) {
    const off = this.on(event, (...args) => {
      off();
      fn(...args);
    });
    return off;
  }

  off(event, fn) {
    this.#listeners.get(event)?.delete(fn);
  }

  emit(event, ...args) {
    const set = this.#listeners.get(event);
    if (!set || set.size === 0) return false;
    [...set].forEach((fn) => fn(...args));
    return true;
  }
}

Đáp án 9.6Mini Dependency Injection container
Code đáp án
class Container {
  #instances = new Map();
  #overrides = new Map();
  #resolving = new Set();

  override(token, impl) {
    this.#overrides.set(token, impl);
  }

  resolve(token) {
    if (this.#instances.has(token)) return this.#instances.get(token);
    if (this.#resolving.has(token)) {
      throw new Error(`Phụ thuộc vòng tại ${token.name}`);
    }

    this.#resolving.add(token);
    const Impl = this.#overrides.get(token) ?? token;
    const deps = (Impl.inject ?? []).map((d) => this.resolve(d));
    const instance = new Impl(...deps);
    this.#resolving.delete(token);

    this.#instances.set(token, instance);
    return instance;
  }
}

async function withRetry(fn, retries = 2) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (e) {
      if (!e.retryable || attempt >= retries) throw e;
      console.log(`Thử lại lần ${attempt + 1}: ${e.message}`);
    }
  }
}

async function fetchAll(api) {
  const all = [];
  let page = 1;
  let lastPage = 1;
  do {
    const res = await withRetry(() => api.getOrders(page));
    all.push(...res.data);
    lastPage = res.lastPage;
    page++;
  } while (page <= lastPage);
  return all;
}

async function getTopCustomers(api, limit) {
  const orders = await fetchAll(api);
  const totals = orders
    .filter((o) => o.status === 'paid')
    .reduce((acc, o) => {
      acc[o.customer] = (acc[o.customer] ?? 0) + o.total;
      return acc;
    }, {});

  return Object.entries(totals)
    .map(([customer, total]) => ({ customer, total }))
    .toSorted((a, b) => b.total - a.total)
    .slice(0, limit);
}

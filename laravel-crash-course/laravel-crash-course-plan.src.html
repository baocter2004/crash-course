P.4 Array — chỉ có MỘT kiểu, gánh cả object của JS

// Indexed array (như Array của JS) $tags = ['php', 'laravel']; // Associative array (như Object/Map của JS) — RẤT hay gặp trong Laravel $post = ['title' => 'Hello', 'views' => 10]; echo $post['title']; // truy cập bằng [] chứ không phải . foreach ($post as $key => $value) { /* ... */ } // Các hàm array phải thuộc lòng array_map(fn ($p) => $p['title'], $posts); // map array_filter($posts, fn ($p) => $p['views'] > 5); // filter (GIỮ NGUYÊN key!) array_reduce($posts, fn ($c, $p) => $c + $p['views'], 0); array_column($posts, 'title'); // lấy 1 cột từ mảng 2 chiều array_keys($post); array_values($post); count($post); in_array('php', $tags, true); // tham số 3 = so sánh strict
Bẫy: array_map đảo thứ tự tham số so với array_filter (callback trước / mảng trước), và array_filter giữ nguyên key cũ nên mảng kết quả có thể "khuyết index" — khi trả JSON sẽ thành object thay vì array. Dùng array_values(...) để reset index. Trong Laravel bạn sẽ ít gặp chuyện này vì Collection (collect($arr)->map()->filter()->values()) xử lý gọn hơn nhiều — nhưng phải biết array thuần trước.

PART 00 — NỀN TẢNG

Kiến trúc tổng thể & Request Lifecycle

Mục tiêu: Hiểu Laravel là gì ở tầng kiến trúc trước khi code. Laravel không phải "một đống helper function" — nó là một IoC container (kho chứa và tự lắp ráp object) được bootstrap bởi các Service Provider, rồi đẩy request qua một pipeline middleware. Hiểu 3 khái niệm đó là hiểu 80% Laravel.

1. Điểm khởi đầu: public/index.php → bootstrap/app.php

Mọi request HTTP đều được web server (Nginx/Apache) trỏ vào đúng một file duy nhất: public/index.php. File này rất ngắn, nó chỉ làm 3 việc: nạp Composer autoloader, lấy instance ứng dụng từ bootstrap/app.php, rồi gọi handleRequest().

// bootstrap/app.php — "file cấu hình trung tâm" của Laravel 11+ return Application::configure(basePath: dirname(__DIR__)) ->withRouting( web: __DIR__.'/../routes/web.php', api: __DIR__.'/../routes/api.php', // chỉ có sau khi chạy install:api commands: __DIR__.'/../routes/console.php', health: '/up', ) ->withMiddleware(function (Middleware $middleware) { // đăng ký / sắp xếp middleware ở đây }) ->withExceptions(function (Exceptions $exceptions) { // tuỳ biến cách báo lỗi & render lỗi ở đây })->create();
Điểm khác biệt lớn so với Laravel 10 trở về trước: từ Laravel 11, các file app/Http/Kernel.php, app/Exceptions/Handler.php, app/Providers/RouteServiceProvider.php đã bị xoá. Toàn bộ cấu hình middleware, exception, routing gom hết về bootstrap/app.php. Nếu bạn xem tutorial cũ trên YouTube/blog mà thấy sửa Kernel.php → đó là tài liệu lỗi thời, đừng làm theo.

2. Service Container (IoC Container) — trái tim của Laravel

Service Container là một "kho" biết cách tự khởi tạo object và tự tiêm dependency. Khi bạn type-hint một class ở constructor (hoặc ở tham số method của controller), Laravel dùng PHP Reflection để đọc kiểu dữ liệu đó, tự tạo instance rồi truyền vào — bạn không bao giờ phải tự new PostService().

class PostController extends Controller { public function __construct( protected PostService $posts, // container tự resolve và tiêm vào ) {} }

Đây chính xác là cơ chế Dependency Injection bạn đã gặp ở NestJS. Khác biệt: NestJS đọc metadata do decorator sinh ra lúc compile; Laravel đọc trực tiếp type-hint qua Reflection lúc runtime — không cần đăng ký class vào một mảng providers nào cả nếu class đó có thể tự khởi tạo được.

3. Service Providers — nơi mọi thứ được "lắp ráp"

Service Provider là các class chịu trách nhiệm khai báo cho container biết: "gặp interface X thì dựng class Y", "service Z là singleton"... Mỗi provider có 2 method, và thứ tự chạy của chúng rất quan trọng:

MethodChạy khi nàoĐược làm gì
register()Chạy trước, trên TẤT CẢ providerChỉ được đăng ký binding vào container. KHÔNG được dùng service của provider khác (vì có thể chưa đăng ký xong)
boot()Chạy sau, khi mọi provider đã register xongLàm mọi thứ cần dùng tới service khác: định nghĩa rate limiter, gate/policy, event listener, Model::preventLazyLoading()...

Danh sách provider của ứng dụng nằm ở bootstrap/providers.php; provider mặc định của bạn là app/Providers/AppServiceProvider.php.

4. Request Lifecycle — thứ tự một request đi qua hệ thống

Đây là sơ đồ cần thuộc. So với NestJS (Middleware → Guard → Interceptor → Pipe → Handler), Laravel gom gọn hơn: mọi thứ chặn/lọc request đều là middleware, còn validate dữ liệu thì nằm ở Form Request.

Client Request HTTP request tới web server → trỏ vào public/index.php ▼ Bootstrap Nạp autoloader, tạo Application (container), đọc .env + config, đăng ký & boot toàn bộ Service Provider ▼ Global Middleware Chạy cho MỌI request: TrustProxies, HandleCors, ValidatePostSize, TrimStrings, ConvertEmptyStringsToNull... ▼ Router Tìm route khớp URI + HTTP method. Không khớp → NotFoundHttpException (404) ▼ Route Middleware Middleware của nhóm api + của riêng route: SubstituteBindings (route model binding), auth:sanctum, throttle, can... Đây là chỗ tương đương Guard bên NestJS ▼ Form Request Nếu controller type-hint một FormRequest → validate TRƯỚC khi thân hàm chạy. Sai → tự trả 422. Tương đương ValidationPipe + DTO bên NestJS ▼ Controller Method controller chạy, gọi Model/Service, trả về Resource hoặc response ▼ Response ← Middleware Response đi NGƯỢC ra qua đúng chuỗi middleware đó rồi send() về client ▼ Terminate Middleware có terminate() chạy SAU khi response đã gửi (FastCGI) ⚠ Bất kỳ bước nào throw exception → nhảy thẳng tới Exception Handler (withExceptions) → render thành response lỗi. Request có Accept: application/json → Laravel tự trả JSON.

5. Facade thực chất là gì?

Khi bạn viết Route::get(...) hay DB::table(...), trông như gọi static method, nhưng thực ra không có static method nào cả. Facade là một class proxy: nó bắt lời gọi static bằng __callStatic(), hỏi container lấy instance thật đang được đăng ký, rồi gọi method instance trên đó. Nghĩa là Facade chỉ là "lối tắt cú pháp" để lấy đồ trong container — object bên dưới vẫn mock được khi test (Queue::fake(), Event::fake(), Storage::fake() ở các Part sau đều là ứng dụng của điều này).

Khởi tạo dự án & cấu trúc thư mục

Mục tiêu: Dựng được project Laravel chạy được, hiểu mỗi thư mục dùng để làm gì, và bật chế độ API (điều mà Laravel không bật sẵn).

1.1 Cài đặt

Yêu cầu: PHP 8.3 trở lên (Laravel 13 hỗ trợ PHP 8.3–8.5) và Composer. Kiểm tra bằng php -v và composer -V.

1.2 Bật API — bước bắt buộc, rất nhiều người quên

Laravel 11+ không tạo sẵn file routes/api.php. Dự án mới chỉ có routes/web.php. Muốn làm API bạn phải chạy:

php artisan install:api

Lệnh này làm 3 việc: (1) cài Laravel Sanctum (authentication bằng API token — Part 09), (2) tạo file routes/api.php, (3) thêm dòng api: vào withRouting() trong bootstrap/app.php đồng thời publish migration bảng personal_access_tokens.

PART 02

Routing & Controllers cho API

Mục tiêu: Map được HTTP request tới đúng method trong Controller theo chuẩn REST, và hiểu Route Model Binding — thứ giúp bạn xoá sạch code "tìm bản ghi, không thấy thì trả 404".

2.1 Khai báo route

// routes/api.php — nhớ: đã tự có prefix /api use App\Http\Controllers\PostController; Route::get('/posts', [PostController::class, 'index']); Route::post('/posts', [PostController::class, 'store']); Route::get('/posts/{post}', [PostController::class, 'show']); Route::put('/posts/{post}', [PostController::class, 'update']); Route::delete('/posts/{post}', [PostController::class, 'destroy']);

2.2 apiResource — viết 5 route trên bằng 1 dòng

Route::apiResource('posts', PostController::class);
VerbURIMethodRoute name
GET/api/postsindexposts.index
POST/api/postsstoreposts.store
GET/api/posts/{post}showposts.show
PUT/PATCH/api/posts/{post}updateposts.update
DELETE/api/posts/{post}destroyposts.destroy

apiResource khác resource ở chỗ nó bỏ 2 route create và edit — hai route đó chỉ để trả về form HTML, API thuần không cần. Sinh controller tương ứng bằng:

# --api: sinh sẵn 5 method (không có create/edit) # --model: type-hint sẵn model Post vào tham số (bật route model binding) # --requests: sinh luôn StorePostRequest + UpdatePostRequest php artisan make:controller PostController --api --model=Post --requests
PUT hay PATCH? Chuẩn HTTP: PUT = thay thế toàn bộ resource (client gửi đủ mọi field), PATCH = sửa một phần. apiResource đăng ký cả hai cùng trỏ vào update(), nên bạn tự quyết định: nếu rule validation cho phép thiếu field (sometimes) thì thực chất bạn đang làm PATCH — hãy để client gọi PATCH cho đúng ngữ nghĩa.

2.3 Route Model Binding — tính năng "ăn tiền" nhất

Thay vì nhận $id rồi tự query, bạn type-hint thẳng Model. Middleware SubstituteBindings (có sẵn trong nhóm api) sẽ tự query bản ghi theo giá trị URI, và tự trả 404 nếu không tìm thấy:

// Route: /api/posts/{post} → tên tham số {post} phải TRÙNG tên biến $post public function show(Post $post) { return $post; // tới được đây nghĩa là chắc chắn tìm thấy }

So sánh với NestJS: bên đó bạn phải viết ParseIntPipe + tự throw new NotFoundException() trong service. Laravel làm sẵn cả hai. Muốn tìm theo cột khác id (ví dụ slug) — có 2 cách:

// Cách 1: khai ngay tại route (chỉ áp dụng cho route đó) Route::get('/posts/{post:slug}', [PostController::class, 'show']); // Cách 2 (Laravel 13): gắn attribute lên Model → áp dụng cho MỌI route bind Post use Illuminate\Database\Eloquent\Attributes\RouteKey; #[RouteKey('slug')] class Post extends Model { }
Đã đối chiếu docs Routing 13.x: #[RouteKey('slug')] đúng là attribute chính thức (namespace Illuminate\Database\Eloquent\Attributes\RouteKey). Cách cũ getRouteKeyName() vẫn dùng được. Với route lồng (/posts/{post}/comments/{comment}), Laravel tự "scope" comment phải thuộc post đó khi bạn dùng custom key — xem Part 08.

2.4 Controller gọn gàng

namespace App\Http\Controllers; use App\Models\Post; class PostController extends Controller { public function index() { return Post::latest()->paginate(15); } public function store(StorePostRequest $request) // validate tự chạy trước { $post = Post::create($request->validated()); return response()->json($post, 201); // 201 Created } public function destroy(Post $post) { $post->delete(); return response()->noContent(); // 204 No Content } }
Nguyên tắc "controller mỏng": controller chỉ nên làm 3 việc — nhận request đã validate, gọi model/service, trả response. Không đặt logic nghiệp vụ phức tạp, không viết query dài dòng ở đây. Part 21 sẽ chỉ chỗ đặt những thứ đó.

2.5 Nhóm route & middleware

Route::apiResource('posts', PostController::class)->only(['index', 'show']); // Nhóm route cần đăng nhập Route::middleware('auth:sanctum')->group(function () { Route::apiResource('posts', PostController::class)->except(['index', 'show']); }); // Hoặc chỉ định theo từng action — gọn hơn (docs 13.x: middlewareFor / withoutMiddlewareFor) Route::apiResource('posts', PostController::class) ->middlewareFor(['store', 'update', 'destroy'], 'auth:sanctum'); // Hoặc khai ngay trên controller bằng attribute (Laravel 13) use Illuminate\Routing\Attributes\Controllers\Middleware; #[Middleware('auth:sanctum', except: ['index', 'show'])] class PostController extends Controller { }
Việc cần làm:
  1. Tạo PostController bằng make:controller --api
  2. Đăng ký Route::apiResource('posts', ...) trong routes/api.php
  3. Tạm thời trả về mảng cứng trong bộ nhớ (chưa cần database) cho đủ 5 action
  4. Chạy php artisan route:list --path=api, đối chiếu với bảng ở mục 2.2
  5. Test 5 endpoint bằng Postman/curl. Nhớ gửi header Accept: application/json — thiếu header này Laravel sẽ trả HTML khi có lỗi
  6. Thử gọi /api/posts/999 và quan sát response khi chưa có model binding
PART 03

Service Container, DI & Service Providers

Mục tiêu: Tách logic nghiệp vụ ra khỏi Controller, và hiểu container tự lắp ráp object như thế nào — nền tảng để code test được.

3.1 Tự động resolve (zero config)

Container đọc type-hint bằng Reflection và tự dựng object. Với class không có dependency đặc biệt, bạn không cần khai báo gì cả:

namespace App\Services; class PostService { public function publish(Post $post): Post { $post->update(['published_at' => now()]); return $post; } } // Controller — chỉ cần type-hint, container lo phần còn lại class PostController extends Controller { public function __construct(protected PostService $posts) {} }
Khác NestJS ở đây: Nest bắt buộc khai providers: [PostsService] trong module, quên là lỗi "Nest can't resolve dependencies". Laravel không cần — chỉ khi bạn muốn can thiệp vào cách dựng object mới phải đăng ký binding.

3.2 Khi nào phải bind thủ công

Khi type-hint là interface (container không biết dựng interface), hoặc khi cần truyền tham số đặc biệt, hoặc muốn dùng chung một instance:

// app/Providers/AppServiceProvider.php public function register(): void { // bind: mỗi lần resolve tạo instance MỚI (giống scope TRANSIENT bên Nest) $this->app->bind(PaymentGateway::class, StripeGateway::class); // singleton: tạo 1 lần, dùng lại mãi (giống scope DEFAULT bên Nest) $this->app->singleton(PostService::class, function ($app) { return new PostService(config('services.posts.per_page')); }); // scoped: 1 instance cho mỗi request (quan trọng khi chạy Octane — Part 22) $this->app->scoped(RequestContext::class, fn () => new RequestContext()); }
Cách bindVòng đời instanceTương đương NestJS
bindTạo mới mỗi lần được resolveScope.TRANSIENT
singletonMột instance duy nhất cho cả appScope.DEFAULT
scopedMột instance cho mỗi requestScope.REQUEST
Lưu ý về vòng đời process: PHP-FPM mặc định huỷ toàn bộ bộ nhớ sau mỗi request — nên "singleton" của Laravel thực chất chỉ sống trong một request, khác hẳn Node.js/NestJS nơi singleton sống suốt đời tiến trình server. Đây là lý do bạn không thể "cache dữ liệu vào thuộc tính static" trong Laravel như bên Nest. Ngoại lệ: Queue worker và Octane là process sống lâu — lúc đó singleton sống thật, và scoped mới trở nên quan trọng.

3.3 Bind theo interface — vì sao nên làm

// Contract interface NotifierInterface { public function send(string $msg): void; } // Ở AppServiceProvider::register() $this->app->bind(NotifierInterface::class, MailNotifier::class);

Lợi ích: đổi MailNotifier → SlackNotifier chỉ sửa 1 dòng; khi test thì bind sang một fake object. Đây là nguyên tắc Dependency Inversion — code phụ thuộc vào abstraction, không phụ thuộc implementation cụ thể.

3.4 register() vs boot() — lỗi hay gặp

public function register(): void { // ✔ CHỈ đăng ký binding ở đây $this->app->singleton(PostService::class); // ✘ SAI: Route::pattern(...) / RateLimiter::for(...) — lúc này provider khác có thể chưa sẵn sàng } public function boot(): void { // ✔ Mọi thứ cần dùng service khác thì đặt ở đây RateLimiter::for('api', fn ($request) => Limit::perMinute(60)->by($request->user()?->id ?: $request->ip())); Model::preventLazyLoading(! $this->app->isProduction()); // Part 08 }
Việc cần làm:
  1. Tạo app/Services/PostService.php, chuyển toàn bộ logic từ Controller sang đây
  2. Inject PostService vào Controller qua constructor — xác nhận chạy được mà KHÔNG cần đăng ký gì
  3. Tạo interface PostRepositoryInterface + một implementation, bind trong AppServiceProvider::register(), rồi type-hint interface đó ở service
  4. Thử cố tình bind sai (bind interface tới class không tồn tại) để xem thông báo lỗi của container trông thế nào
  5. Trả lời: vì sao RateLimiter::for() phải nằm trong boot() chứ không phải register()
PART 04

Database: Migration, Eloquent Model, Factory & Seeder

Mục tiêu: Thay mảng cứng bằng database thật, hiểu Eloquent (Active Record) khác gì TypeORM Repository (Data Mapper), và biết bảo vệ ứng dụng khỏi lỗ hổng mass assignment.

4.1 Migration — "git cho cấu trúc database"

Migration là file PHP mô tả một thay đổi cấu trúc bảng, chạy theo thứ tự thời gian. Nhờ nó, đồng đội chỉ cần git pull + php artisan migrate là có database giống hệt bạn.

php artisan make:migration create_posts_table public function up(): void { Schema::create('posts', function (Blueprint $table) { $table->id(); // BIGINT UNSIGNED AUTO_INCREMENT PK $table->string('title'); $table->text('body'); $table->timestamp('published_at')->nullable(); $table->timestamps(); // tạo created_at + updated_at }); } public function down(): void { Schema::dropIfExists('posts'); // dùng khi rollback }
LệnhTác dụng
php artisan migrateChạy các migration chưa chạy
php artisan migrate:rollbackLùi lại batch migration gần nhất
php artisan migrate:fresh --seedXoá sạch mọi bảng, chạy lại từ đầu + seed. Chỉ dùng ở local
php artisan migrate:statusXem migration nào đã chạy
php artisan db:show / db:table postsXem tổng quan DB / cấu trúc 1 bảng ngay trong terminal
Nguyên tắc: migration đã chạy trên production thì không sửa lại file cũ — phải tạo migration mới để thay đổi. Sửa file cũ sẽ khiến máy người khác (đã chạy rồi) không bao giờ nhận được thay đổi đó. Đây là điểm khác hẳn synchronize: true của TypeORM mà bạn dùng bên NestJS — Laravel không bao giờ "tự đoán" schema.

4.3 Mass assignment — bảo mật, không phải thủ tục

Muốn dùng Post::create($data), bạn phải khai báo field nào được phép gán hàng loạt. Đây là cơ chế chống việc kẻ tấn công gửi thêm field lạ (ví dụ is_admin=1, user_id=999) rồi ghi thẳng vào DB.

use Illuminate\Database\Eloquent\Attributes\Fillable; #[Fillable(['title', 'body', 'published_at'])] // cú pháp Laravel 13 class Post extends Model { protected function casts(): array // ép kiểu khi đọc/ghi { return [ 'published_at' => 'datetime', // string trong DB → Carbon object trong PHP 'is_featured' => 'boolean', // 0/1 → true/false 'status' => PostStatus::class, // enum backed (P.6) — DB lưu 'draft', PHP nhận enum ]; } }
Cú pháp cũ vẫn chạy: protected $fillable = ['title','body']; vẫn hoạt động bình thường và bạn sẽ gặp nó ở 99% tutorial trên mạng. Attribute #[Fillable] là cách viết mới mà docs Laravel 13 dùng — chọn một kiểu và dùng nhất quán trong cả project.
Bổ sung sau audit — bật "strict mode" cho Eloquent khi dev. Docs khuyến nghị đặt trong AppServiceProvider::boot(): Model::preventLazyLoading(! $this->app->isProduction()); // bắt N+1 (Part 08) Model::preventSilentlyDiscardingAttributes($this->app->isLocal()); // field không nằm trong fillable → throw thay vì âm thầm bỏ Không có 2 dòng này, việc quên thêm field vào fillable sẽ khiến create() "thành công" nhưng cột đó rỗng — bug rất khó tìm.

4.4 CRUD với Eloquent

// ĐỌC Post::all(); // mọi bản ghi — cẩn thận với bảng lớn Post::find(1); // không thấy → null Post::findOrFail(1); // không thấy → ModelNotFoundException → tự thành 404 Post::where('title', 'like', '%nest%')->get(); Post::latest()->paginate(15); // phân trang, kèm sẵn meta/links (Part 12) // TẠO $post = Post::create(['title' => 'Hello', 'body' => '...']); // SỬA $post->update(['title' => 'Updated']); // XOÁ $post->delete(); // UPSERT / firstOrCreate — hay dùng khi import Post::firstOrCreate(['slug' => 'hello'], ['title' => 'Hello', 'body' => '...']);
Active Record vs Data Mapper: Eloquent là Active Record — bản thân object $post biết cách tự lưu/xoá chính nó ($post->save()). TypeORM bên NestJS là Data Mapper — entity chỉ là dữ liệu thuần, phải nhờ repository.save(entity). Active Record viết nhanh hơn nhiều; đổi lại model gánh cả logic truy vấn nên dễ phình to — vì vậy dự án lớn hay tách bớt sang Service/Action/Query class (Part 21).

  7. Thử bỏ field ra khỏi fillable rồi gọi create() — quan sát exception nhờ strict mode ở bước 4
PART 05

Validation với Form Request

Mục tiêu: Đảm bảo dữ liệu client gửi lên luôn đúng định dạng trước khi chạm tới Controller — và trả lỗi theo đúng chuẩn 422 Unprocessable Content.

5.1 Hai cách validate

// Cách 1 — validate ngay trong controller (nhanh, cho case đơn giản) public function store(Request $request) { $data = $request->validate([ 'title' => ['required', 'string', 'max:255'], 'body' => ['required', 'string'], ]); return Post::create($data); } # Cách 2 — Form Request (KHUYẾN NGHỊ cho API): tách rule ra class riêng php artisan make:request StorePostRequest namespace App\Http\Requests; use Illuminate\Foundation\Http\FormRequest; class StorePostRequest extends FormRequest { public function authorize(): bool { return true; // false → tự trả 403 Forbidden (Part 19 sẽ dùng thật) } public function rules(): array { return [ 'title' => ['required', 'string', 'max:255', 'unique:posts,title'], 'body' => ['required', 'string', 'min:10'], ]; } public function messages(): array { return ['title.required' => 'Tiêu đề là bắt buộc.']; } }

5.2 Cơ chế: nó chạy lúc nào?

Bạn chỉ cần type-hint Form Request vào controller. Container thấy class đó kế thừa FormRequest nên tự chạy validate ngay khi resolve tham số — tức là trước khi dòng code đầu tiên trong thân method chạy:

public function store(StorePostRequest $request) { // Tới được đây = dữ liệu CHẮC CHẮN đã hợp lệ return Post::create($request->validated()); }

Thứ tự thực tế: authorize() → rules() → (sai thì 422 / không có quyền thì 403) → thân method.

5.3 Format lỗi 422 mà Laravel trả về

Nếu request có header Accept: application/json (hoặc là XHR), Laravel trả về đúng cấu trúc sau — hãy nhớ nó vì frontend sẽ dựa vào đây:

HTTP/1.1 422 Unprocessable Content { "message": "The title field is required. (and 1 more error)", "errors": { "title": ["The title field is required."], "body": ["The body field must be at least 10 characters."] } }
Bẫy kinh điển: nếu không gửi header Accept: application/json, Laravel coi đây là request từ browser nên trả về redirect 302 kèm lỗi trong session thay vì JSON 422. Rất nhiều người tưởng API bị lỗi trong khi chỉ là thiếu header. Part 07 sẽ chỉ cách ép mọi request /api/* luôn nhận JSON.

PART 06

API Resources — tầng transform response

Mục tiêu: Không bao giờ trả model thô ra ngoài. Có một tầng riêng quyết định "API này công khai những field nào, định dạng ra sao".

6.1 Vì sao không return thẳng model?

Trả return $post; thì Laravel tự serialize toàn bộ cột trong bảng thành JSON. Ba vấn đề: (1) rò rỉ dữ liệu — thêm cột internal_note vào DB là API tự động phơi ra; (2) API vỡ hợp đồng — đổi tên cột trong DB làm frontend chết theo; (3) không kiểm soát được định dạng (ngày tháng, field tính toán). API Resource giải quyết cả ba.

php artisan make:resource PostResource namespace App\Http\Resources; use Illuminate\Http\Request; use Illuminate\Http\Resources\Json\JsonResource; class PostResource extends JsonResource { public function toArray(Request $request): array { return [ 'id' => $this->id, 'title' => $this->title, 'body' => $this->body, 'created_at' => $this->created_at?->toIso8601String(), ]; } }
Vì sao gọi được $this->id khi $this là Resource chứ không phải Post? Vì JsonResource proxy mọi lời gọi property/method xuống model bên dưới. Model thật nằm ở $this->resource.

6.2 Dùng trong Controller

// 1 bản ghi return new PostResource($post); return $post->toResource(); // cách gọn (Laravel 12+), tự tìm PostResource // nhiều bản ghi return PostResource::collection(Post::all()); return Post::latest()->paginate(15)->toResourceCollection(); // kèm status code & header return (new PostResource($post))->response()->setStatusCode(201);
Đã đối chiếu docs: toResource() tự tìm class theo quy ước — model App\Models\Post → tìm App\Http\Resources\PostResource (hoặc Post) ở namespace Http\Resources gần model nhất; có thể chỉ định tường minh $post->toResource(CustomPostResource::class).

6.3 Data wrapping — response trông thế nào

Mặc định Laravel bọc kết quả trong key data:

{ "data": { "id": 1, "title": "Hello" } }

Khi phân trang qua Resource collection, response luôn có thêm links và meta:

{ "data": [ ... ], "links": { "first": "...?page=1", "last": "...?page=4", "prev": null, "next": "...?page=2" }, "meta": { "current_page": 1, "from": 1, "last_page": 4, "per_page": 15, "to": 15, "total": 54 } }

Muốn bỏ lớp data, gọi JsonResource::withoutWrapping() trong AppServiceProvider::boot(). Lưu ý: response phân trang vẫn giữ data vì cần chỗ đặt meta/links.

Khuyến nghị: giữ nguyên wrapping mặc định. Một API mà "khi thì trả object, khi thì trả object bọc data" là nguồn bug bất tận cho frontend. Chọn một kiểu và giữ nhất quán toàn bộ endpoint — đây cũng là bài học bạn đã rút ra khi làm TransformInterceptor bên NestJS.

6.4 Field có điều kiện

return [ 'id' => $this->id, 'title' => $this->title, // chỉ trả khi thoả điều kiện 'secret' => $this->when($request->user()?->isAdmin(), $this->secret), // chỉ trả khi relation ĐÃ được eager load → tránh N+1 (xem Part 08) 'comments' => CommentResource::collection($this->whenLoaded('comments')), // chỉ trả khi đã loadCount('comments') 'comments_count' => $this->whenCounted('comments'), ];

6.5 JSON:API Resource (mới ở Laravel 13)

Laravel 13 bổ sung JsonApiResource — tạo response đúng chuẩn jsonapi.org: có type, attributes, relationships, hỗ trợ ?include= và sparse fieldsets ?fields[posts]=title, tự set header application/vnd.api+json.

Đã đối chiếu docs: class chính xác là Illuminate\Http\Resources\JsonApi\JsonApiResource; muốn kiểm soát chi tiết thì override toAttributes(Request $request): array (có thể trả closure để lazy-evaluate field nặng). Relationship chỉ được serialize khi client yêu cầu qua ?include=. Docs gợi ý dùng kèm package Spatie Query Builder để parse filter/sort phía request.

Có nên dùng JSON:API ngay? Với crash course này thì không cần — hãy làm JsonResource thường cho vững đã. Biết là nó tồn tại, để khi gặp dự án yêu cầu chuẩn JSON:API thì không phải tự viết tay.

Việc cần làm:
  1. Tạo PostResource, chỉ expose: id, title, body, created_at (ISO 8601)
  2. Sửa cả 5 action trong Controller để trả về Resource thay vì model thô
  3. Endpoint index: dùng paginate(15) + resource collection, kiểm tra response có meta và links
  4. Thêm 1 cột "nội bộ" vào bảng posts (vd internal_note), xác nhận nó KHÔNG lộ ra API nhờ Resource
  5. Đảm bảo status code đúng: store → 201, destroy → 204
PART 07

Middleware & Exception Handling

Mục tiêu: Tự viết middleware, và chuẩn hoá toàn bộ response lỗi của API về một format duy nhất — đây là thứ phân biệt API "tập viết" với API dùng được thật.

7.1 Viết middleware

php artisan make:middleware LogRequests public function handle(Request $request, Closure $next): Response { $start = microtime(true); $response = $next($request); // đi sâu vào app Log::info('API', [ 'method' => $request->method(), 'uri' => $request->path(), 'status' => $response->status(), 'ms' => round((microtime(true) - $start) * 1000), ]); return $response; // PHẢI return, nếu không request bị treo }

Middleware là pipeline hai chiều: code trước $next() chạy khi request đi vào, code sau $next() chạy khi response đi ra. Nó gánh vai trò của cả Middleware + Guard + Interceptor bên NestJS. Muốn làm việc nặng sau khi đã trả response (ghi log ra dịch vụ ngoài...), thêm method terminate(Request $request, Response $response) — Laravel gọi nó sau khi response đã gửi tới client (cần FastCGI).

7.2 Đăng ký middleware

// bootstrap/app.php ->withMiddleware(function (Middleware $middleware) { $middleware->append(LogRequests::class); // global, chạy cho mọi request $middleware->api(prepend: ['throttle:api']); // thêm vào nhóm api $middleware->alias(['admin' => EnsureUserIsAdmin::class]); // đặt tên ngắn })

Sau khi có alias, gắn vào route: Route::delete(...)->middleware('admin'). Middleware nhận tham số qua dấu : — ví dụ 'role:editor,publisher' tương ứng handle($request, $next, ...$roles).

Đã đối chiếu docs Middleware 13.x — nhóm mặc định: nhóm api chỉ có đúng 1 middleware SubstituteBindings; throttle:api và EnsureFrontendRequestsAreStateful (Sanctum SPA) đều bị comment sẵn. Nghĩa là rate limit KHÔNG bật sẵn — muốn có thì tự thêm như trên (chi tiết Part 10). Nhóm web ở Laravel 13 dùng PreventRequestForgery (tên mới của middleware CSRF, có kiểm tra origin) — API stateless không dùng tới.

7.3 Exception Handling — chuẩn hoá lỗi JSON

Mặc định Laravel đã trả lỗi dạng JSON khi request có Accept: application/json: 404 cho model không tìm thấy, 422 cho validation, 401 khi chưa đăng nhập. Nhưng format mỗi loại một kiểu. Muốn thống nhất, cấu hình trong withExceptions():

// bootstrap/app.php ->withExceptions(function (Exceptions $exceptions) { // 1) Mọi request /api/* đều được coi là muốn nhận JSON (hết bẫy 302 ở Part 05) $exceptions->shouldRenderJsonWhen(fn (Request $request, Throwable $e) => $request->is('api/*') || $request->expectsJson()); // 2) Đổi thông điệp 404 cho API (mặc định message rỗng, khó debug) $exceptions->render(function (NotFoundHttpException $e, Request $request) { if ($request->is('api/*')) { return response()->json(['message' => 'Resource not found.'], 404); } }); // 3) Không report một số exception vô hại (giảm rác log) $exceptions->dontReport([PostAlreadyPublishedException::class]); })
Bài học từ audit dự án NestJS của bạn: khi tự viết filter/handler lỗi, tuyệt đối đừng bọc lồng payload lỗi. Nếu response thành {"message": {"message": "...", "statusCode": 404}} thì client phải đọc body.message.message — sai chuẩn và rất dễ gây bug. Format lỗi nên phẳng và giống nhau ở mọi status code, ví dụ: { message, errors?, status }.

7.4 Exception nghiệp vụ tự viết

php artisan make:exception PostAlreadyPublishedException class PostAlreadyPublishedException extends Exception { // Có method render() → Laravel tự gọi, không cần khai gì trong bootstrap/app.php public function render(Request $request): JsonResponse { return response()->json([ 'message' => 'Bài viết này đã được publish trước đó.', ], 409); // 409 Conflict } }

Trong service chỉ cần throw new PostAlreadyPublishedException(); — không cần try/catch ở controller. Ngoài render(), exception còn có thể khai report() để tự quyết cách ghi log, và context() để thêm dữ liệu vào log.

PART 09

Authentication với Laravel Sanctum

Mục tiêu: Hiểu trọn luồng đăng ký → đăng nhập → cấp token → bảo vệ route → đăng xuất, và biết vì sao password phải hash chứ không được mã hoá.

9.1 Sanctum là gì — và không phải là gì

Sanctum đã được cài sẵn khi bạn chạy php artisan install:api ở Part 01. Nó giải quyết 2 bài toán tách biệt:

  • API token (personal access token, giống token của GitHub): token là chuỗi random, được hash SHA-256 rồi lưu vào bảng personal_access_tokens. Client gửi kèm header Authorization: Bearer . → Đây là phần ta dùng.
  • SPA authentication: dùng session cookie thay vì token, cho frontend cùng domain. Không dùng trong crash course này.
Sanctum khác JWT thế nào? Token Sanctum là opaque (chuỗi vô nghĩa, phải tra DB mới biết của ai) — nên thu hồi được ngay lập tức bằng cách xoá dòng trong DB. JWT là self-contained (chứa payload, verify bằng chữ ký, không cần tra DB) — nhanh hơn nhưng không thu hồi được trước khi hết hạn. Với API thường, Sanctum là lựa chọn mặc định đúng. Cần OAuth2 đầy đủ thì mới dùng Laravel Passport.

9.2 Chuẩn bị model User

use Laravel\Sanctum\HasApiTokens; class User extends Authenticatable { use HasApiTokens, HasFactory, Notifiable; // thêm HasApiTokens }

Trait HasApiTokens mang lại: createToken(), quan hệ tokens(), currentAccessToken(), tokenCan(). Trait Notifiable (có sẵn) sẽ dùng ở Part 20.

9.3 Luồng đầy đủ

10.3 Rate limiting

Nhớ Part 07: nhóm api của Laravel 13 không bật throttle sẵn. Làm 2 bước:

PART 13 — MỚI

Database Transactions

Mục tiêu: Đảm bảo nhiều thao tác ghi "thành công cùng nhau hoặc thất bại cùng nhau" (atomicity), hiểu bẫy deadlock, và — quan trọng nhất trong Laravel — hiểu vì sao job/event bắn ra bên trong transaction có thể chạy trước khi dữ liệu được commit.

13.1 Vấn đề transaction giải quyết

Tạo 1 Post, đồng thời tạo Comment chào mừng đầu tiên và cộng posts_count cho user. Nếu bước 2 hoặc 3 lỗi, bạn còn lại dữ liệu nửa vời. Transaction đảm bảo: hoặc cả 3 cùng được ghi (COMMIT), hoặc cả 3 cùng bị hoàn tác (ROLLBACK) như chưa từng xảy ra.

13.2 Cách chuẩn — DB::transaction()

use Illuminate\Support\Facades\DB; public function publish(User $author, array $data): Post { return DB::transaction(function () use ($author, $data) { $post = $author->posts()->create($data); $post->comments()->create(['body' => 'Chào mừng bài viết đầu tiên!']); $author->increment('posts_count'); return $post; // giá trị return của closure = giá trị return của DB::transaction() }); }

Cơ chế: BEGIN → chạy closure → không lỗi thì COMMIT; closure throw bất kỳ exception nào thì ROLLBACK rồi ném lại exception đó cho bạn (không nuốt). Không cần try/catch. Mọi query Eloquent/Query Builder bên trong closure đều nằm trong cùng transaction (Laravel dùng chung 1 connection).

Đối chiếu NestJS: bên TypeORM bạn phải gọi mọi thứ qua manager được truyền vào callback, dùng nhầm repository thường là "thoát" khỏi transaction. Laravel không có vấn đề đó — vì transaction gắn với connection, và mọi model đều đi qua connection đó trong cùng request. Đơn giản hơn hẳn.

13.3 Deadlock & retry

DB::transaction(function () { // ... }, attempts: 5); // gặp deadlock → tự chạy lại tối đa 5 lần trước khi ném lỗi

Deadlock xảy ra khi 2 transaction chờ khoá của nhau (A giữ dòng 1 chờ dòng 2, B giữ dòng 2 chờ dòng 1). Database sẽ tự giết 1 trong 2. Tham số attempts cho Laravel tự chạy lại transaction bị giết — với điều kiện closure của bạn idempotent (chạy lại không gây tác dụng phụ kép: không gửi mail, không dispatch job bên trong closure).

13.4 Thủ công — khi cần kiểm soát từng bước

DB::beginTransaction(); try { // ... DB::commit(); } catch (\Throwable $e) { DB::rollBack(); throw $e; }

Chỉ dùng khi thực sự cần (ví dụ commit từng phần trong vòng lặp lớn). 95% trường hợp DB::transaction() đủ và an toàn hơn — quên rollBack() trong catch là để lại transaction treo, khoá bảng cho tới khi request kết thúc.

13.5 Bẫy lớn nhất: job/event bắn ra TRONG transaction

DB::transaction(function () { $post = Post::create([...]); // ① INSERT — nhưng CHƯA commit ProcessPost::dispatch($post); // ② job vào queue NGAY LẬP TỨC }); // ③ COMMIT ở đây Queue worker (process khác) nhận job ở giữa ② và ③: → SELECT * FROM posts WHERE id = 42 → KHÔNG THẤY (chưa commit) → ModelNotFoundException → hoặc tệ hơn: transaction rollback, job vẫn chạy với dữ liệu không tồn tại

Cách xử lý (theo docs Queues 13.x):

// Cách 1 — từng job: chỉ đẩy vào queue sau khi transaction ngoài cùng commit ProcessPost::dispatch($post)->afterCommit(); // Cách 2 — toàn cục: config/queue.php, connection đang dùng 'after_commit' => true, // Event cũng vậy: implement ShouldDispatchAfterCommit trên class Event (Part 15) // Listener queued: implement ShouldQueueAfterCommit

Nếu transaction rollback, job/event có afterCommit sẽ bị bỏ luôn — đúng như mong muốn. Nếu không có transaction nào đang mở, chúng được dispatch ngay như thường.

13.6 Implicit commit — lệnh làm transaction "tự commit" mà bạn không biết

Trong MySQL, các lệnh DDL (CREATE TABLE, ALTER TABLE, TRUNCATE...) gây implicit commit: chạy chúng qua DB::statement() bên trong transaction sẽ commit toàn bộ transaction ngầm, Laravel không hay biết. Đừng chạy migration/schema trong transaction nghiệp vụ.

13.7 Quan sát query — công cụ debug hiệu năng

// AppServiceProvider::boot() DB::listen(function (QueryExecuted $query) { Log::debug($query->toRawSql(), ['ms' => $query->time]); // toRawSql: SQL đã gắn binding }); // Cảnh báo khi 1 request tốn > 500ms cho database DB::whenQueryingForLongerThan(500, function (Connection $connection, QueryExecuted $event) { Log::warning('Slow request: total DB time > 500ms'); });
Việc cần làm:
  1. Viết PostService::publish() tạo Post + Comment đầu tiên + tăng posts_count trong 1 DB::transaction()
  2. Test rollback: tạm throw new \RuntimeException('test') sau bước tạo Comment → gọi API → xác nhận cả Post lẫn Comment đều KHÔNG có trong DB (assertDatabaseMissing)
  3. Viết test Pest chứng minh DB::transaction() ném lại đúng exception gốc (expect(fn () => ...)->toThrow(RuntimeException::class))
  4. Thêm DB::listen() log ra storage/logs, gọi endpoint index và đếm số query — dùng lại cho task N+1 ở Part 08
  5. Đọc trước mục 13.5, giữ lại trong đầu — Part 14 sẽ tái hiện đúng bug này bằng job thật
PART 14 — MỚI (chuyên sâu)

Queue & Jobs

Mục tiêu: Đưa mọi việc chậm (gửi mail, xử lý ảnh, gọi API bên thứ 3, export) ra khỏi request HTTP; hiểu trọn vòng đời một job từ dispatch() tới worker, retry, fail; và vận hành worker đúng cách. Đây là phần phân biệt rõ nhất "biết Laravel" và "làm Laravel thật".

14.1 Mô hình: queue là gì trong bức tranh PHP

Request HTTP (PHP-FPM, chết sau vài chục ms) Worker (php artisan queue:work — process sống mãi) ┌───────────────────────────────┐ ┌──────────────────────────────────┐ │ Controller nhận POST /posts │ │ vòng lặp vô tận: │ │ Post::create(...) │ ghi 1 dòng │ pop job từ queue │ │ ProcessPost::dispatch($post) ─┼──────────────► │ unserialize → new ProcessPost │ │ return 202 Accepted (ngay) │ vào jobs table │ gọi handle() │ └───────────────────────────────┘ / Redis list │ OK → xoá job │ lỗi → retry/fail│ └──────────────────────────────────┘

Vì PHP-FPM không có event loop, "chạy nền" đồng nghĩa với ghi mô tả công việc vào một kho (queue) để một process PHP khác (worker) lấy ra chạy. Đây là câu trả lời của Laravel cho async của Node — và nó có lợi thế: worker crash không kéo theo web, scale worker độc lập với web.

14.3 Viết job

php artisan make:job ProcessPost namespace App\Jobs; use App\Models\Post; use App\Services\ImageOptimizer; use Illuminate\Contracts\Queue\ShouldQueue; use Illuminate\Foundation\Queue\Queueable; use Illuminate\Queue\Attributes\Tries; use Illuminate\Queue\Attributes\Timeout; use Illuminate\Queue\Attributes\Backoff; #[Tries(3)] // tối đa 3 lần thử #[Timeout(120)] // 1 lần chạy tối đa 120s #[Backoff([10, 60, 300])] // chờ 10s, rồi 60s, rồi 300s giữa các lần retry class ProcessPost implements ShouldQueue { use Queueable; public function __construct( public Post $post, // Eloquent model: chỉ serialize ID, worker tự load lại từ DB ) {} // Container inject dependency vào handle() y như controller public function handle(ImageOptimizer $optimizer): void { $optimizer->optimize($this->post->cover_path); $this->post->update(['processed_at' => now()]); } // Gọi khi job THẤT BẠI HẲN (hết số lần thử) public function failed(\Throwable $e): void { $this->post->update(['processing_error' => $e->getMessage()]); } }
  • ShouldQueue — interface đánh dấu "đẩy vào queue" (không có nó, dispatch() sẽ chạy đồng bộ).
  • Queueable — trait mang các method onQueue(), delay(), afterCommit()... và lo việc serialize.
  • SerializesModels: model trong constructor chỉ được lưu ID + class vào payload; khi worker chạy, nó query lại DB. Hệ quả: dữ liệu luôn mới nhất, nhưng nếu bản ghi đã bị xoá thì job fail với ModelNotFoundException. Quan hệ đã load() cũng được serialize kèm — dùng #[WithoutRelations] để payload nhẹ.
Đã đối chiếu docs Queues 13.x: các attribute #[Tries], #[Timeout], #[Backoff], #[MaxExceptions], #[FailOnTimeout], #[WithoutRelations] đều chính thức (namespace Illuminate\Queue\Attributes\*). Cách cũ public int $tries = 3; / public function backoff(): array / retryUntil(): DateTime vẫn hoạt động. Quy tắc quan trọng: timeout của job phải nhỏ hơn retry_after trong config/queue.php (mặc định 90s) — nếu không, job đang chạy dở có thể bị worker khác nhặt lên chạy trùng.

14.4 Dispatch — mọi biến thể

// Đẩy vào queue mặc định ProcessPost::dispatch($post); // Queue riêng (để worker ưu tiên) / connection riêng ProcessPost::dispatch($post)->onQueue('media'); ProcessPost::dispatch($post)->onConnection('redis'); // Chạy sau 10 phút ProcessPost::dispatch($post)->delay(now()->addMinutes(10)); // Chờ transaction ngoài cùng commit rồi mới vào queue (Part 13.5) ProcessPost::dispatch($post)->afterCommit(); // Có điều kiện ProcessPost::dispatchIf($post->hasCover(), $post); // Ép chạy ngay trong request, bỏ qua queue (debug / test) ProcessPost::dispatchSync($post); // Chạy sau khi đã trả response, trong CÙNG process — chỉ cho việc dưới vài giây ProcessPost::dispatchAfterResponse($post); // Laravel 13 — định tuyến tập trung trong AppServiceProvider::boot(): Queue::route(ProcessPost::class, connection: 'redis', queue: 'media'); Queue::route([ ProcessPost::class => ['redis', 'media'], SendDigest::class => 'emails', ]);
Controller nên trả 202: khi bạn dispatch rồi return, việc chưa xong. Trả 202 Accepted + id để client hỏi lại trạng thái, đừng trả 200 như thể đã hoàn tất.

14.6 Chạy worker đúng cách

php artisan queue:work # worker cơ bản php artisan queue:work --queue=media,default --tries=3 # ưu tiên queue 'media' trước 'default' php artisan queue:work --max-jobs=1000 --max-time=3600 # tự thoát sau 1000 job / 1 giờ (chống rò rỉ RAM) php artisan queue:listen # nạp lại code mỗi job — CHẬM, chỉ để dev php artisan queue:restart # báo mọi worker thoát êm sau job hiện tại
Điểm sống còn khi deploy (theo docs): queue:work nạp code app một lần rồi chạy mãi trong RAM — sửa code xong mà không queue:restart thì worker vẫn chạy code CŨ. Mọi script deploy phải có dòng php artisan queue:restart. Lệnh này chỉ "ra hiệu", nên cần Supervisor (Part 22) để tự khởi động worker mới.

Ở local, mở terminal thứ 2 chạy php artisan queue:work song song với php artisan serve. Hoặc php artisan queue:listen nếu đang sửa code job liên tục (nó tự nạp lại code, đổi lại chậm hơn).

14.7 Job middleware — kiểm soát cách job chạy

use Illuminate\Queue\Middleware\{WithoutOverlapping, RateLimited}; use Illuminate\Queue\Middleware\{ThrottlesExceptions, Skip}; public function middleware(): array { return [ // Không cho 2 job của cùng 1 post chạy song song; job đến sau được release, thử lại sau 60s (new WithoutOverlapping($this->post->id))->releaseAfter(60), // Giới hạn tốc độ (ví dụ API bên thứ 3 cho 100 req/phút) — limiter khai trong RateLimiter::for('external-api', ...) new RateLimited('external-api'), // Nếu 10 exception trong 5 phút → tạm dừng job loại này 5 phút (circuit breaker) new ThrottlesExceptions(10, 5 * 60), // Bỏ qua job khi điều kiện đúng (ví dụ post đã bị xoá) Skip::when(fn () => $this->post->trashed()), ]; }
Khi nào dùng cái nào: WithoutOverlapping cho tài nguyên chỉ được 1 người sửa (ví dụ số dư, file); RateLimited khi gọi API ngoài có quota; ThrottlesExceptions khi dịch vụ ngoài đang sập — thay vì 1.000 job cùng fail và retry dồn dập, tạm "ngắt cầu dao".

PART 15 — MỚI

Events, Listeners & Observers

Mục tiêu: Tách "chuyện gì vừa xảy ra" khỏi "ai cần phản ứng" — để thêm hành vi mới (gửi mail, ghi log, cập nhật thống kê) mà không sửa lại service gốc. Và hiểu event kết hợp với queue/transaction thế nào.

15.1 Vì sao cần event

Không có event, PostService::publish() sẽ phình ra: tạo post → gửi mail cho follower → cập nhật search index → bắn webhook → ghi audit log... Mỗi tính năng mới lại phải sửa hàm này. Với event, service chỉ nói "PostPublished" rồi xong; mỗi listener tự lo phần mình, thêm/bớt listener không đụng service.

15.2 Tạo event & listener

php artisan make:event PostPublished php artisan make:listener SendPostPublishedNotification --event=PostPublished // app/Events/PostPublished.php — chỉ là "túi dữ liệu" class PostPublished { use Dispatchable, SerializesModels; public function __construct(public Post $post) {} } // app/Listeners/SendPostPublishedNotification.php class SendPostPublishedNotification implements ShouldQueue // queued → chạy ở worker (Part 14) { public function handle(PostPublished $event): void { $event->post->author->notify(new PostPublishedNotification($event->post)); // Part 20 } } // Bắn event — trong service PostPublished::dispatch($post); // hoặc event(new PostPublished($post));
Đã đối chiếu docs Events 13.x — Event Discovery: Laravel tự quét thư mục app/Listeners, thấy method handle() hoặc __invoke() có type-hint event nào thì tự đăng ký cho event đó — không cần khai báo trong EventServiceProvider như Laravel ≤10 (file đó không còn tồn tại). Muốn quét thêm thư mục khác: ->withEvents(discover: [__DIR__.'/../app/Domain/*/Listeners']) trong bootstrap/app.php. Kiểm tra bằng php artisan event:list. Production nên chạy php artisan event:cache (có trong optimize).

15.3 Listener chạy nền — cấu hình queue ngay trên listener

15.5 Model events & Observer — event có sẵn của Eloquent

Cache & Atomic Locks

Mục tiêu: Giảm tải database bằng cache đúng cách (và biết khi nào cache gây hại), dùng atomic lock để chống race condition — thứ mà PHP "mỗi request một process" đặc biệt dễ dính.

16.1 Vì sao PHP cần cache ngoài process

16.3 Stale-while-revalidate — Cache::flexible()

Giải quyết vấn đề "cache hết hạn đúng lúc 100 request cùng tới → 100 request cùng tính lại" (cache stampede). Việc tính lại chạy trong deferred function sau khi response đã gửi.

16.4 Xoá cache đúng lúc (cache invalidation)

Câu hỏi khó nhất của cache không phải "cất thế nào" mà "xoá khi nào". Ba chiến lược, kết hợp với Observer (Part 15):

// 1) TTL ngắn — chấp nhận dữ liệu trễ vài phút, đơn giản nhất Cache::remember('posts:latest', 60, ...); // 2) Xoá chủ động khi dữ liệu đổi — trong PostObserver::saved / deleted Cache::forget('posts:latest'); Cache::forget("post:{$post->id}"); // 3) Tags — xoá cả nhóm (chỉ redis/memcached) Cache::tags(['posts'])->put("post:{$post->id}", $post, 3600); Cache::tags(['posts'])->flush(); // xoá mọi key gắn tag 'posts'
Đừng cache quá sớm. Cache là lớp phức tạp thêm (bug "sửa rồi mà vẫn thấy cũ" là kinh điển). Thứ tự đúng: (1) sửa N+1 và thêm index, (2) đo bằng Telescope/Pulse, (3) chỉ cache chỗ thật sự nóng. Và không bao giờ cache dữ liệu theo user mà không đưa user id vào key.

16.5 Atomic lock — chống race condition

Tình huống: 2 request cùng lúc "thanh toán đơn #42". Cả 2 đọc status = pending, cả 2 chuyển sang paid, trừ tiền 2 lần. Transaction (Part 13) không đủ nếu logic có gọi API ngoài. Cần khoá:

$lock = Cache::lock("order:{$order->id}:pay", 10); // khoá tối đa 10s if ($lock->get()) { // lấy được khoá → xử lý try { $this->charge($order); } finally { $lock->release(); } } else { throw new ConflictException('Đơn hàng đang được xử lý.'); // 409 } // Gọn hơn: closure tự release Cache::lock("order:{$order->id}:pay", 10)->get(fn () => $this->charge($order)); // Chờ tối đa 5s để lấy khoá thay vì từ chối ngay Cache::lock('report', 10)->block(5, fn () => $this->generate()); // Laravel 13: giới hạn đồng thời — tối đa 3 tiến trình cùng chạy Cache::funnel('image-processing')->limit(3)->releaseAfter(60)->block(10) ->then(fn () => $this->process(), fn () => throw new TooManyRequestsHttpException());

Job middleware WithoutOverlapping (Part 14.7) và Schedule::withoutOverlapping() (Part 17) đều dùng chính cơ chế lock này bên dưới. Lock cần store hỗ trợ (database/redis/memcached/file/array) và phải là store chung giữa mọi server.

Giải quyết việc gọi Cache::get('settings') 50 lần trong 1 request (50 round-trip Redis) — memo() ghi nhớ trong bộ nhớ process cho tới hết request/job.

  2. Xoá cache đó trong PostObserver khi post được tạo/sửa/xoá — chứng minh "tạo post mới → GET thấy ngay"
  3. Đổi Cache::remember thành Cache::flexible([60, 300], ...), đọc log để thấy việc tính lại chạy sau response

  5. Test: dùng Cache::spy() hoặc config(['cache.default' => 'array']) để assert key được ghi/xoá đúng

Mail & Notifications (queued)

Mục tiêu: Gửi thông báo qua nhiều kênh (mail, database, Slack...) bằng một class duy nhất, luôn đẩy qua queue, và test được mà không gửi mail thật.

Mailable = 1 email cụ thể (template, subject). Notification = "một thông báo" có thể đi qua nhiều kênh (mail, database, broadcast, slack, vonage), kênh mail bên trong vẫn dùng MailMessage. Với ứng dụng thật, gần như luôn viết Notification — nó bao trùm Mailable và cho user tự chọn kênh.

21.2 Action class — đơn vị nghiệp vụ test được

namespace App\Actions\Posts; final class PublishPostAction { public function __construct( private readonly ImageOptimizer $images, // container inject như mọi class khác ) {} public function handle(User $author, PublishPostData $data): Post { return DB::transaction(function () use ($author, $data) { $post = $author->posts()->create($data->toArray()); ProcessPost::dispatch($post)->afterCommit(); PostPublished::dispatch($post); // ShouldDispatchAfterCommit return $post; }); } } // Controller public function store(StorePostRequest $request, PublishPostAction $action) { $post = $action->handle($request->user(), PublishPostData::fromRequest($request)); return $post->toResource()->response()->setStatusCode(202); }

21.4 Enum cho trạng thái — hết "magic string"

enum PostStatus: string { case Draft = 'draft'; case Scheduled = 'scheduled'; case Published = 'published'; public function canTransitionTo(self $next): bool { return match($this) { self::Draft => in_array($next, [self::Scheduled, self::Published]), self::Scheduled => $next === self::Published, self::Published => false, }; } } // Model: cast → đọc ra enum, ghi vào string protected function casts(): array { return ['status' => PostStatus::class]; } // Validation: Rule::enum(PostStatus::class) // Query: Post::where('status', PostStatus::Published) // Route binding: /posts/status/{status} với type-hint PostStatus $status → tự ép, sai → 404

21.5 Query scope — đặt tên cho truy vấn

use Illuminate\Database\Eloquent\Attributes\Scope; class Post extends Model { #[Scope] protected function published(Builder $query): void { $query->whereNotNull('published_at')->where('published_at', '<=', now()); } #[Scope] protected function popular(Builder $query, int $min = 100): void { $query->where('views', '>=', $min); } } Post::published()->popular(500)->latest()->paginate();
Đã đối chiếu docs Eloquent 13.x: #[Scope] trên method protected là cách mới; cách cũ public function scopePublished(Builder $query) vẫn chạy. Global scope (áp mọi query) dùng #[ScopedBy([TenantScope::class])].

PART 22 — MỚI

Production: deploy, worker, Octane, quan sát hệ thống

Mục tiêu: Hiểu một app Laravel chạy thật cần những process nào, deploy sao cho không mất job, và nhìn thấy được chuyện gì đang xảy ra bên trong.

22.1 Một app Laravel production gồm 3 loại process

Nginx ──► PHP-FPM (nhiều worker) : xử lý HTTP request ← Part 00 php artisan queue:work : xử lý job (Supervisor giữ sống) ← Part 14 cron → schedule:run : mỗi phút, chạy task tới giờ ← Part 17 Redis : cache + queue + lock ← Part 14, 16 MySQL/PostgreSQL : dữ liệu

Thiếu bất kỳ mảnh nào: web vẫn lên nhưng mail không gửi, lịch không chạy, lock không hoạt động — lỗi "âm thầm" khó thấy nhất.

22.2 Supervisor — giữ worker luôn sống

Theo docs Queues: stopwaitsecs phải lớn hơn thời gian chạy của job dài nhất, nếu không Supervisor kill job giữa chừng khi restart. --max-time cho worker tự thoát định kỳ (Supervisor khởi động lại) — chống rò rỉ bộ nhớ ở process sống lâu.

22.4 Horizon — dashboard cho queue Redis

composer require laravel/horizon → php artisan horizon:install. Horizon thay queue:work bằng php artisan horizon (1 process quản lý nhiều worker, tự cân bằng theo tải), kèm dashboard /horizon: job đang chạy, fail, thời gian chờ, throughput. Chỉ dùng với driver redis. Với app có queue nghiêm túc, đây là mặc định.

22.5 Octane — khi PHP-FPM không đủ nhanh

composer require laravel/octane → chạy app bằng Swoole/FrankenPHP/RoadRunner: app boot 1 lần rồi giữ trong RAM, mỗi request không phải nạp lại framework → nhanh gấp nhiều lần. Đổi lại, mô hình P.1 thay đổi: singleton sống qua nhiều request, biến static "dính" giữa các request. Vì thế Part 03 nhấn mạnh scoped() và Octane docs có danh sách "dependency injection pitfalls". Chỉ cân nhắc Octane khi đã đo và biết bottleneck là bootstrap chứ không phải DB.

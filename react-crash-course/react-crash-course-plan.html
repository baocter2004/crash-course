PART J — NỀN TẢNG NGÔN NGỮ

JavaScript ES6+ cho React

Mục tiêu: Nắm chắc các tính năng JS mà React dùng ở mọi dòng code. Phần lớn lỗi "React khó hiểu" thực chất là lỗi chưa vững JS — đặc biệt là tham chiếu vs giá trị, closure và bất biến (immutability).

J.1 let / const và scope

const user = { name: 'Nhat' };              // const = KHÔNG gán lại được biến
user.name = 'Long';                           // vẫn sửa được thuộc tính bên trong!
// user = {}                     ✘ TypeError: Assignment to constant variable

let count = 0; count++;                    // let khi cần gán lại
// var: KHÔNG dùng nữa (scope theo function, bị hoisting khó lường)
Quy tắc: mặc định dùng const, chỉ đổi sang let khi thật sự cần gán lại. Trong React bạn gần như chỉ dùng const.

J.2 Tham chiếu vs giá trị — gốc rễ của mọi bug React

// Primitive (number, string, boolean, null, undefined) → so sánh theo GIÁ TRỊ
1 === 1                   // true
'a' === 'a'               // true

// Object / Array / Function → so sánh theo THAM CHIẾU (địa chỉ ô nhớ)
[] === []                  // false !!
{} === {}                  // false !!
const a = [1]; const b = a; a === b     // true (cùng 1 địa chỉ)
Vì sao cực kỳ quan trọng: React quyết định "có cần render lại không" bằng phép so sánh Object.is (gần như ===). Nên: (1) sửa trực tiếp mảng/object trong state → React thấy vẫn cùng tham chiếu → không render lại; (2) truyền {} hay [] mới mỗi lần render vào props/dependency → React thấy luôn khác → render lại / chạy effect vô hạn. Hai lỗi này chiếm phần lớn bug của người mới.

J.3 Destructuring, spread & rest

// Destructuring object — cách nhận props chuẩn của React
const { title, salary = 'Thoả thuận' } = job;      // có giá trị mặc định
const { company: { name } } = job;                  // lồng nhau

// Destructuring array — cách useState trả về
const [count, setCount] = useState(0);

// Spread — TẠO BẢN SAO MỚI (cốt lõi của immutability)
const updated  = { ...job, title: 'Mới' };        // copy object + ghi đè 1 field
const appended = [...jobs, newJob];                 // copy mảng + thêm phần tử

// Rest — gom phần còn lại
const { id, ...rest } = job;
function Button({ children, ...props }) { }         // pattern rất hay dùng
Spread chỉ copy NÔNG (shallow): {...job} copy được field cấp 1, nhưng job.company vẫn là cùng một object. Muốn sửa dữ liệu lồng nhau phải spread từng cấp: { ...job, company: { ...job.company, name: 'X' } }.

J.4 Arrow function & this

const double = (x) => x * 2;                // return ngầm
const make   = (x) => ({ value: x });       // trả object → PHẢI bọc ()
const sum    = (a, b) => { return a + b; };  // có {} thì phải return tường minh

Arrow function không có this riêng — nó mượn this của scope bao ngoài. Với React function component (kiểu hiện đại) bạn gần như không đụng tới this nữa; chỉ cần nhớ điều này khi đọc code class component cũ.

J.6 Toán tử hay dùng trong JSX

{ isLoading && <Spinner /> }                    // short-circuit: true thì render
{ jobs.length > 0 ? <List /> : <Empty /> }         // ternary: if/else
{ job?.company?.name }                            // optional chaining: null thì undefined
{ job.salary ?? 'Thoả thuận' }                   // nullish: chỉ thay khi null/undefined
Bẫy kinh điển: {jobs.length && <List />} — nếu length === 0, JS trả về số 0 và React sẽ in ra chữ "0" trên màn hình. Luôn ép sang boolean: {jobs.length > 0 && ...}. Ngoài ra: ?? khác || — || thay cả 0 và '' (falsy), ?? chỉ thay null/undefined.

J.8 Bất đồng bộ: Promise, async/await, fetch

async function getJobs() {
  try {
    const res = await fetch('/api/jobs');

    // QUAN TRỌNG: fetch KHÔNG throw khi server trả 404/500 — phải tự kiểm tra
    if (!res.ok) throw new Error(`HTTP ${res.status}`);

    return await res.json();
  } catch (err) {
    console.error(err);
    throw err;
  }
}

Ba trạng thái của Promise: pending → fulfilled / rejected. await chỉ dùng được trong hàm async, và hàm async luôn trả về Promise. Đây là lý do bạn không được khai async cho callback của useEffect trực tiếp (Part 06).

J.9 Closure — nền tảng để hiểu Hooks

function counter() {
  let count = 0;                    // biến này "sống" nhờ closure
  return () => ++count;              // hàm trong nhớ được biến ngoài
}
const inc = counter();
inc(); inc();                             // 1, 2

Closure = hàm "nhớ" được môi trường nơi nó được tạo ra. React dùng closure cho toàn bộ hệ thống hook: mỗi lần render tạo ra một closure mới với giá trị state của lần render đó. Hiểu điều này là hiểu vì sao có hiện tượng "stale closure" — hàm trong setTimeout hay useEffect nhìn thấy giá trị state cũ của lần render mà nó được tạo (Part 03 & 06).

PART 00 — NỀN TẢNG

React hoạt động thế nào

Mục tiêu: Hiểu React thực sự làm gì trước khi viết component. React không phải framework đầy đủ như NestJS/Laravel — nó chỉ là thư viện dựng giao diện, với một ý tưởng trung tâm: UI = f(state). Bạn mô tả "với state này thì giao diện trông thế nào", React lo phần cập nhật DOM.

0.1 Declarative vs Imperative

// Imperative (DOM thuần) — bạn ra lệnh từng bước
const el = document.createElement('div');
el.textContent = count;
document.body.appendChild(el);
// và mỗi lần count đổi, bạn phải TỰ tìm đúng node để sửa

// Declarative (React) — bạn mô tả kết quả mong muốn
return <div>{count}</div>;
// count đổi → React tự tính ra cần sửa gì trên DOM

0.2 Virtual DOM & Reconciliation

Mỗi lần render, component của bạn trả về một cây object mô tả UI (React element — chính là Virtual DOM). React so sánh cây mới với cây của lần render trước (reconciliation), tính ra tập thay đổi nhỏ nhất, rồi mới đụng vào DOM thật. DOM thật rất chậm; so sánh object trong RAM thì nhanh — đó là toàn bộ lý do Virtual DOM tồn tại.

Trigger Lần render đầu, hoặc setState được gọi │ ▼ Render phase React gọi hàm component của bạn để lấy cây element mới. Phase này phải THUẦN KHIẾT: không sửa biến ngoài, không gọi API, không đụng DOM. React có thể huỷ và chạy lại phase này bất cứ lúc nào │ ▼ Diff/Reconcile So cây mới với cây cũ theo vị trí và type; với danh sách thì so theo key │ ▼ Commit phase Áp thay đổi lên DOM thật, cập nhật ref, rồi chạy useEffect │ ▼ Browser paint Trình duyệt vẽ lại màn hình
Hệ quả cần nhớ: "render" không đồng nghĩa với "cập nhật DOM". React có thể gọi lại hàm component của bạn nhiều lần mà DOM không đổi gì cả. Vì vậy: không bao giờ đặt side-effect (gọi API, ghi localStorage, sửa biến toàn cục) trực tiếp trong thân component.

0.3 Luồng dữ liệu một chiều

Dữ liệu chảy từ cha xuống con qua props. Con không được sửa props. Muốn con tác động lên cha thì cha truyền xuống một hàm callback. Nhờ ràng buộc này, khi UI sai bạn luôn truy ngược được nguồn dữ liệu — khác hẳn kiểu two-way binding dễ rối.

0.4 StrictMode: vì sao code chạy 2 lần

// src/main.jsx
<StrictMode>
  <App />
</StrictMode>

Ở chế độ development, StrictMode cố ý gọi component 2 lần và chạy effect 2 lần (mount → unmount → mount lại) để phát hiện sớm: component không thuần khiết, effect thiếu cleanup. Ở production nó không làm vậy. Thấy log in 2 lần là bình thường — đừng gỡ StrictMode, hãy sửa code cho đúng.

Mục tiêu: Hiểu state là gì, vì sao phải cập nhật bất biến, và 3 hiểu lầm phổ biến nhất về setState.

3.1 useState cơ bản

const [count, setCount] = useState(0);
//        ▲ giá trị hiện tại  ▲ hàm cập nhật    ▲ giá trị khởi tạo (chỉ dùng ở lần render ĐẦU)

setCount(count + 1);           // yêu cầu React render lại với giá trị mới
Quy tắc Hook (bắt buộc): chỉ gọi hook ở cấp cao nhất của component — không đặt trong if, vòng lặp, hàm lồng. Lý do: React nhận diện hook theo thứ tự gọi; đổi thứ tự giữa các lần render là hỏng toàn bộ state. ESLint plugin react-hooks sẽ bắt lỗi này.

3.2 Hiểu lầm 1: "setState cập nhật ngay lập tức"

function handleClick() {
  setCount(count + 1);
  console.log(count);       // ✘ vẫn in ra giá trị CŨ
}

Vì count là hằng số của lần render này (closure — xem Part J). setCount chỉ lên lịch một lần render mới; giá trị mới chỉ xuất hiện ở lần render sau. Đây gọi là "state là một snapshot".

3.3 Hiểu lầm 2: gọi setState nhiều lần thì cộng dồn

setCount(count + 1);
setCount(count + 1);
setCount(count + 1);           // count = 0 → kết quả là 1, KHÔNG phải 3

// ✔ Dùng dạng hàm cập nhật (updater) khi giá trị mới phụ thuộc giá trị cũ
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);
setCount((prev) => prev + 1);      // → 3 ✔

React gộp (batch) các lần setState trong cùng một sự kiện thành một lần render — đó là tối ưu, không phải bug. Dạng updater đọc giá trị mới nhất trong hàng đợi nên luôn đúng.

3.4 Hiểu lầm 3: sửa trực tiếp object/array trong state

// ✘ SAI — mutate: React so sánh thấy CÙNG tham chiếu → không render lại
jobs.push(newJob);

// ✔ ĐÚNG — luôn tạo object/array MỚI

setJobs(jobs.filter((j) => j.id !== id));                        // xoá
setJobs(jobs.map((j) => j.id === id ? { ...j, ...patch } : j));  // sửa
setForm({ ...form, title: 'X' });                              // sửa 1 field

  • Đừng để state trùng lặp. Lưu selectedId thay vì lưu cả object selectedJob đã copy.
  • Nhóm state đi cùng nhau. Form nhiều field → một object, hoặc dùng useReducer (Part 08).
  • Đặt state ở đúng độ cao. Càng gần nơi dùng càng tốt; chỉ nâng lên cha khi có 2 component cùng cần (Part 08).
State vs biến thường: biến thường (let x = 0) bị reset sau mỗi lần render và không kích hoạt render. State thì được React giữ lại giữa các lần render và kích hoạt render khi đổi. Cần giữ giá trị mà không muốn render lại (id của timer, tham chiếu DOM) → dùng useRef.

4.2 Key dùng để làm gì

Key không phải để "React biết thứ tự". Key là danh tính của phần tử: nó cho React biết "element này ở lần render trước và lần này là cùng một thứ". Nhờ đó React biết nên giữ lại DOM node cùng toàn bộ state bên trong component đó, hay huỷ đi tạo mới.

Cách đặt keyĐánh giá

key={Math.random()}✘ Rất tệ — key đổi mỗi lần render → React huỷ và dựng lại toàn bộ, mất state, mất focus, chậm
Không có keyReact cảnh báo trong console và mặc định dùng index
Bug thật khi dùng index làm key: danh sách có ô input; bạn gõ vào ô thứ 2 rồi xoá phần tử thứ 1. Vì key là index, React tưởng phần tử 2 "chính là" phần tử 1 cũ → giữ nguyên state của ô cũ → nội dung bạn gõ nhảy sang dòng khác. Đây là loại bug rất khó truy vết nếu không hiểu key.

useEffect — dùng đúng và dùng ít

Mục tiêu: Hiểu Effect thực sự dùng để làm gì (đồng bộ với hệ thống bên ngoài React), và nhận ra phần lớn useEffect người mới viết là không cần thiết.

6.1 Cú pháp & 3 dạng dependency

useEffect(() => {
  // side effect: gọi API, subscribe, timer, đọc/ghi localStorage...

  return () => {
    // CLEANUP: chạy trước lần effect kế tiếp và khi component unmount
  };
}, [deps]);
DependencyChạy khi nào
[]Chỉ sau lần render đầu (mount). Dev + StrictMode: chạy 2 lần
[a, b]Sau mount, và mỗi khi a hoặc b đổi tham chiếu/giá trị
Không truyềnSau MỌI lần render — hầu như luôn là lỗi

6.2 Cleanup — bắt buộc, không phải tuỳ chọn

useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);       // không có dòng này = rò rỉ timer
}, []);

useEffect(() => {
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, []);

StrictMode cố tình mount → unmount → mount lại ở dev chính là để ép bạn phát hiện thiếu cleanup. Nếu bật app thấy có 2 timer chạy, đó là effect của bạn chưa dọn dẹp.

6.3 Bẫy dependency: vòng lặp vô hạn

// ✘ Object/array tạo mới mỗi lần render → deps LUÔN khác → effect chạy mãi
useEffect(() => { fetchJobs(filters); }, [filters]);  // filters = {} inline ở cha

// ✘ setState không điều kiện trong effect phụ thuộc chính state đó

// ✔ Dùng giá trị primitive làm dependency
useEffect(() => { fetchJobs(type, keyword); }, [type, keyword]);
Đừng bao giờ "im lặng" ESLint bằng cách xoá bớt dependency hoặc thêm // eslint-disable-next-line react-hooks/exhaustive-deps. Cảnh báo đó gần như luôn đúng — nó đang chỉ ra rằng effect của bạn phụ thuộc thứ mà bạn chưa xử lý. Cách sửa đúng: chuyển hàm vào trong effect, dùng dạng updater của setState, hoặc dùng useEffectEvent (mục 6.5).

6.5 useEffectEvent (React 19.2)

import { useEffectEvent, useEffect } from 'react';

function ChatRoom({ roomId, theme }) {
  // Tách phần "sự kiện" ra: đọc được theme MỚI NHẤT nhưng KHÔNG làm effect chạy lại
  const onConnected = useEffectEvent(() => {
    showNotification('Đã kết nối!', theme);
  });

  useEffect(() => {
    const conn = createConnection(roomId);
    conn.on('connected', () => onConnected());
    conn.connect();
    return () => conn.disconnect();
  }, [roomId]);      // ✔ KHÔNG đưa onConnected vào deps — đúng theo quy định của hook này
}

Trước 19.2, đổi theme sẽ khiến effect chạy lại → ngắt và kết nối lại phòng chat một cách vô lý. Effect Event chỉ được gọi bên trong Effect (hoặc Effect Event khác) — không được gọi trong lúc render, không truyền xuống component/hook khác, và không bao giờ đưa vào dependency array (nó cố tình có "identity không ổn định" giữa các lần render). Cần eslint-plugin-react-hooks bản mới để lint đúng quy tắc này.
Việc cần làm:

  2. Cố tình bỏ [] để thấy vòng lặp fetch vô hạn (mở tab Network), rồi sửa

  4. Rà lại toàn bộ code cũ: tìm những useEffect chỉ để tính giá trị dẫn xuất và xoá chúng đi
  5. Viết effect có dependency là object inline để tái hiện vòng lặp, rồi sửa bằng dependency primitive
  6. Thử useEffectEvent cho một effect cần đọc state mới nhất mà không muốn chạy lại

      const res = await fetch(url, { signal: controller.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);

      setJobs(await res.json());
    } catch (err) {
      if (err.name !== 'AbortError') setError(err.message);
    } finally {
      setLoading(false);
    }
  }

  load();
  return () => controller.abort();          // cleanup: huỷ request khi deps đổi/unmount
}, [url]);
Hai lỗi bắt buộc phải tránh: (1) Không viết useEffect(async () => {...}) — hàm async trả về Promise, còn React mong nhận về hàm cleanup. Phải khai hàm async bên trong rồi gọi. (2) Race condition: user gõ tìm kiếm nhanh → nhiều request bay đi; response về không theo thứ tự → kết quả cũ ghi đè kết quả mới. AbortController trong cleanup giải quyết triệt để.

7.3 Custom Hook — tái sử dụng logic có state

// src/hooks/useFetch.js — tên PHẢI bắt đầu bằng "use"
export function useFetch(fetcher, deps = []) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let alive = true;

    setLoading(true);
    fetcher()
      .then((d) => alive && setData(d))
      .catch((e) => alive && setError(e.message))
      .finally(() => alive && setLoading(false));

    return () => { alive = false; };      // chặn setState sau khi unmount
  }, deps);

  return { data, loading, error };
}

// Dùng
const { data: jobs, loading, error } = useFetch(getJobs, []);

8.3 useReducer — gom nhiều state liên quan vào một nơi

function jobsReducer(state, action) {
  switch (action.type) {
    case 'loading': return { ...state, loading: true, error: null };
    case 'success': return { loading: false, error: null, items: action.payload };
    case 'error':   return { ...state, loading: false, error: action.error };
    case 'remove':  return { ...state, items: state.items.filter((j) => j.id !== action.id) };
    default:        throw new Error(`Unknown action: ${action.type}`);
  }
}

15.6 Optimistic update

Giao diện đổi ngay, không chờ server. Nếu lỗi thì phục hồi lại.

export function useDeleteJob(filters: JobFilters) {
  const queryClient = useQueryClient();
  const key = jobKeys.list(filters);

  return useMutation({
    mutationFn: jobsApi.remove,
    onMutate: async (id: number) => {
      await queryClient.cancelQueries({ queryKey: key }); // tránh request cũ ghi đè
      const previous = queryClient.getQueryData<Paginated<Job>>(key);
      queryClient.setQueryData<Paginated<Job>>(key, (old) =>
        old && { ...old, data: old.data.filter((j) => j.id !== id) },
      );
      return { previous }; // đưa sang onError để phục hồi
    },
    onError: (_error, _id, context) => {
      if (context?.previous) queryClient.setQueryData(key, context.previous);
    },
    onSettled: () => queryClient.invalidateQueries({ queryKey: jobKeys.all }),
  });
}

Chỉ dùng cho thao tác hay thành công và dễ phục hồi, như xoá hay thích. Không dùng cho thanh toán.

Đã kiểm chứng bằng test: tải dữ liệu rồi chuyển trang theo URL, hiện lỗi khi API trả 500, và xoá optimistic: dòng biến mất ngay, server trả lỗi thì dòng hiện lại.

Việc cần làm:

  1. Thay toàn bộ useEffect gọi API của dự án bằng useQuery.
  2. Gom key vào một object như jobKeys.
  3. Thêm phân trang và ô tìm kiếm lưu trên URL, kết hợp debounce (bài 4.5 trong tài liệu JS) để không gọi API mỗi lần gõ.
  4. Thêm job bằng useMutation, chứng minh danh sách tự cập nhật.
  5. Xoá job bằng optimistic update. Tắt API rồi bấm xoá, xác nhận dòng hiện lại và có thông báo lỗi.
  6. Mở Network: cùng một trang vào hai lần trong 30 giây thì chỉ có một request.

16.4 Đưa lỗi từ server vào đúng ô

Validate ở client chỉ để trải nghiệm tốt hơn. Server vẫn phải validate, và có lỗi chỉ server mới biết, như email đã tồn tại.

// Laravel trả 422 { message, errors: { title: ['...'] } }
// NestJS (ValidationPipe) trả 400 { message: ['title must be...'] }
export function getFieldErrors(error: unknown): Record<string, string> {
  if (!axios.isAxiosError(error)) return {};
  const errors = error.response?.data?.errors as Record<string, string[]> | undefined;
  if (!errors) return {};
  return Object.fromEntries(Object.entries(errors).map(([field, list]) => [field, list[0]]));
}

export function getErrorMessage(error: unknown): string {
  if (axios.isAxiosError(error)) {
    if (!error.response) return 'Không kết nối được máy chủ';
    const message = error.response.data?.message;
    return Array.isArray(message) ? message.join(', ') : (message ?? `Lỗi ${error.response.status}`);
  }
  return 'Có lỗi xảy ra';
}

17.3 Tự làm mới token

type RetriableConfig = InternalAxiosRequestConfig & { _retried?: boolean };

// Nhiều request cùng nhận 401 chỉ gọi refresh MỘT lần và cùng chờ kết quả đó
let refreshing: Promise<string> | null = null;

export function refreshAccessToken(): Promise<string> {
  refreshing ??= axios
    .post<{ access_token: string }>('/api/auth/refresh', null, { withCredentials: true })
    .then(unwrap)
    .then((res) => {
      setAccessToken(res.data.access_token);
      return res.data.access_token;
    })
    .finally(() => {
      refreshing = null;
    });
  return refreshing;
}

http.interceptors.response.use(
  unwrap,
  async (error: AxiosError) => {
    const original = error.config as RetriableConfig | undefined;
    const isAuthCall = original?.url?.startsWith('/auth/');

    if (error.response?.status !== 401 || !original || original._retried || isAuthCall) {
      throw error;
    }

    original._retried = true; // chặn vòng lặp vô hạn
    try {
      await refreshAccessToken();
      return await http(original); // interceptor request gắn token mới
    } catch (refreshError) {
      setAccessToken(null);
      onSessionExpired();
      throw refreshError;
    }
  },
);

Ba điểm dễ sai:

  • Chỉ refresh một lần: nhiều request cùng nhận 401 phải dùng chung một lần refresh. Nếu mỗi request tự refresh, token xoay vòng sẽ bị coi là dùng lại và cả phiên bị thu hồi.
  • Chặn vòng lặp: cờ _retried để một request chỉ thử lại một lần.
  • Không refresh cho chính /auth/*: đăng nhập sai mà cũng refresh là vô lý.

17.4 AuthContext

interface User {
  id: number;
  email: string;
}
interface AuthValue {
  user: User | null;
  isLoading: boolean;
  login: (email: string, password: string) => Promise<void>;
  logout: () => Promise<void>;
}

const AuthContext = createContext<AuthValue | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    setSessionExpiredHandler(() => setUser(null));
    // F5 làm mất access token trong bộ nhớ: thử lấy lại bằng refresh token trong cookie
    refreshAccessToken()
      .then(() => http.get<User>('/auth/me'))
      .then((res) => setUser(res.data))
      .catch(() => setUser(null))
      .finally(() => setIsLoading(false));
  }, []);

  const value = useMemo<AuthValue>(
    () => ({
      user,
      isLoading,
      login: async (email, password) => {
        const res = await http.post<{ access_token: string }>('/auth/login', { email, password });
        setAccessToken(res.data.access_token);
        const me = await http.get<User>('/auth/me');
        setUser(me.data);
      },
      logout: async () => {
        await http.post('/auth/logout').catch(() => undefined);
        setAccessToken(null);
        setUser(null);
      },
    }),
    [user, isLoading],
  );

  return <AuthContext value={value}>{children}</AuthContext>;
}

export function useAuth() {
  const value = use(AuthContext);
  if (!value) throw new Error('useAuth phải nằm trong AuthProvider');
  return value;
}

lazy cần một module có export default. Nếu component dùng named export thì đổi như ví dụ trên. Component lazy phải nằm trong <Suspense>.

Đã kiểm chứng bằng vite build: JobsPage (0,93 kB) và JobForm (122,9 kB, gồm React Hook Form và Zod) được tách thành file riêng, chỉ tải khi vào đúng trang. File chính 347 kB, trong đó có React, router và TanStack Query.

20.3 Checklist trước khi deploy

Hạng mục Kiểm tra
Chất lượng tsc --noEmit, lint, test đều qua trong CI
Biến môi trường Chỉ biến VITE_* lộ ra trình duyệt: không để secret ở đó

Việc cần làm:

  1. Tách mỗi trang thành một chunk. So sánh kích thước file chính trước và sau.
  2. Dùng dự án chỉ bằng bàn phím, sửa các chỗ không dùng được.
  3. Chạy Lighthouse, đưa điểm Accessibility và Performance lên từ 90.
  4. Deploy lên Vercel hoặc Netlify. Mở thẳng /jobs/1 và bấm F5 để kiểm tra.
